### A Docker image with each release

- **Each release publishes an image** (#133): `ghcr.io/obi-ai-bot/oby-sphere:<version>`, for linux/amd64 and linux/arm64, and `:latest` for the newest release. A pre-release (`v0.4.0-rc.1`) gets its own tag only, so `:latest` stays on the last release. The release workflow builds it from the tagged commit after the tests and the GitHub release, starts it once and checks `/healthz`, then pushes it with the repository's own token, in a job that alone may write packages. Nothing publishes from a pull request or a push to main; CI still builds the image and checks it starts. Each image names this repository, its version and its commit in its OCI labels (on the index too), and carries Docker's provenance attestation and an SBOM ([DEPLOY.md](docs/DEPLOY.md#docker), [SECURITY.md](SECURITY.md#installing-and-updating)).
- **Run it without a checkout.** `docker run … --env-file ~/obysphere.env ghcr.io/obi-ai-bot/oby-sphere:latest`, or pin a version for a server you keep. `obysphere server deploy docker` prints the steps with the version your CLI has, and the keys go in a file, never on the command line.
- **`obysphere server update --docker <container>`** updates a Sphere that runs in Docker on this machine. It pulls the image for your CLI's version (`--tag` picks another), renames the old container `<name>-previous` and stops it, and runs the new image under the same name with the same ports, volumes, variables, labels, restart policy, network, arguments, user, limits and log options. When the new one answers `/healthz` it removes the old one; if it doesn't, the old one comes back as it was. Then the Sphere is recorded in `servers/<name>.json` (no secrets), so `obysphere server update` and `server status` find it like a Vercel deployment; `--url` records its public address. The variables, which hold the keys, reach `docker run` in a 0600 file that's removed at once, never in an argument, and they're hidden in what it shows of docker's errors and the container's log. It refuses, before changing anything, a container that isn't a Sphere, one that Docker Compose runs, one whose data isn't in a volume, one started with `--rm` (stopping it would remove it), a key in the container's arguments, an old `<name>-previous`, a Sphere newer than your CLI (unless you pass `--tag`), and settings it can't carry over (privileged, devices, other namespaces, DNS, tmpfs, several networks, a seccomp profile, other log drivers).
