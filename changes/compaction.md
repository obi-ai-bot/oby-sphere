### Compaction: cold starts stay fast on Redis

- **The Redis log is compacted, so cold starts stay fast** (#126). When the log's tail holds more operations than `SPHERE_COMPACT_EVERY` (5000) and than the snapshot, an instance folds the head into a snapshot, in the background: each member, channel (private ones and direct conversations with their members), admin role and file record once, as it is now; the newest `retainMessages` messages; every audit event from the first; and the counts. It's swapped in with one compare-and-swap script, so two instances compacting at once can't lose an operation or apply one twice; then the head is trimmed. Positions stay absolute (`<prefix>base` + the list's length), and compare-and-append checks both inside its script. An instance that slept through a compaction loads the snapshot and applies only what it hadn't, then the tail. The audit chain stays whole and verifies, `content` hashes included, after compaction and after a cold start. File records and their bytes are kept. `SPHERE_COMPACT_EVERY=0` turns it off.
- **A relay of 0.3 can't misread a compacted log.** The first start of the new version marks the log (`{"t": "compaction"}`, which 0.3 ignores), and nothing is compacted until that mark is an hour old (`SPHERE_COMPACT_WAIT_MS`), so the 0.3 instances from before the deploy have finished. Until then the log stays where 0.3 reads it, and both versions run side by side. The first compaction then moves it (to `<prefix>tail`) and leaves a note at the old key, so a 0.3 relay that runs anyway (a rollback, an old preview) gets an error from Redis instead of reading or appending at the wrong position. It also means 0.3 doesn't start on a compacted Sphere: to keep that way back open for a while after upgrading, set `SPHERE_COMPACT_EVERY=0`.
- **The file store keeps its counts across a restart.** Compacting `messages.jsonl` now ends it with a tally of the counts, so messages past `retainMessages` still count in the console after a restart, as they do on Redis.
